# Discovery and Integrations — LeanIX vs VantageMap

**Scope note.** This 488-page SAP LeanIX document ("Discovery and Integrations", pages 1–488) covers three things: (1) the **reference catalog** (curated best-practice data for business capabilities, applications, IT components, tech categories, with linking/sync/confidence matching); (2) a large set of **out-of-the-box (OOTB) connectors** — SaaS Discovery (Entra ID / Defender / Netskope / Okta / Zscaler), Self-Built Software Discovery (GitHub Enterprise + SBOM), SAP Landscape Discovery, AI Agent Discovery, SAP Cloud ALM, SAP Signavio, ServiceNow, Jira Service Management, Jira Software, Collibra, Apptio, Microsoft Teams, Confluence, OData; and (3) the **foundational integration primitives** that underpin all of the above — the **Integration API + processor model**, **LDIF** (LeanIX Data Interchange Format) inbound/outbound processing with **externalId** identity mapping, **sync scheduling** (full/partial, manual/scheduled), **Synchronization Logging**, the **Self-Built Software Discovery API** (`PUT /technology-discovery/v1/manifests` generic upsert-by-externalId + `POST .../sboms`), the **discovery inbox** review pattern, and **technical users** for programmatic auth. Almost all named *connectors* map to PLANV4 15.6 and are DEFERRED. The analysis below deliberately separates a **deferred connector** (a specific vendor adapter) from a **missing integration primitive** (generic inbound ingestion machinery that VantageMap would need regardless of any vendor).

## Key gaps

Focusing on **core integration primitives** (not the deferred vendor connectors):

- **No externalId / external-system identity mapping (row 4).** No `external_id` column exists on any fact sheet. Every LeanIX connector relies on externalId to make sync idempotent and to unlink/re-link records; VantageMap can only upsert by internal UUID (import) or by display name (bulk upsert). The bulk-upsert schema declares an `externalId` field but silently ignores it. Without this, *any* future automated inbound integration cannot reliably match "the same record from an external system" across runs. This is the foundational gap and a prerequisite for everything else in this domain.
- **No generic inbound ingestion engine / processor + sync-run model (rows 2, 8, 9).** VantageMap's only inbound path is the synchronous CSV/XLSX file import; there is no scheduled/polling ingestion, no processor abstraction, no persisted sync-run with per-action CREATE/UPDATE/DELETE outcomes and error rollups. The only cron job in the codebase drives webhook retries. A real connector story needs a run-tracked ingestion pipeline.
- **No config-as-code / upsert-by-external-key ingestion endpoint (rows 5, 6).** LeanIX's `PUT .../manifests` and manifest schema let an external system declare a fact sheet (plus its relations, tags, subscriptions) and have it created-or-updated by externalId. VantageMap's bulk upsert covers fields but not relations/tags/subscriptions and matches on name. Building this on top of the externalId primitive would be the highest-leverage integration feature.
- **No discovery-inbox / review-before-commit staging (row 10).** Import `preview` mode validates a single file but there is no persisted per-item review queue with statuses, dedup, and confidence scoring — the pattern every LeanIX discovery source uses.
- **No reference catalog (row 11).** No curated, linkable, auto-syncing best-practice dataset. Lower EA-tool-parity priority (it's a content product), but it is the backbone of LeanIX's "populate your inventory fast" value prop.

## Equivalence summary

In this document's domain VantageMap is **weak-to-partial**: it has the right *auth* and *outbound* foundations (technical-user API tokens, HMAC webhooks with durable retry, REST + GraphQL, CSV/XLSX import with preview + batched upsert), but it lacks the core **inbound** integration machinery that makes LeanIX's discovery-and-integrations story work — chiefly a per-fact-sheet **externalId** identity mapping, a generic **processor/sync-run ingestion engine** with scheduling and sync logging, an **upsert-by-external-key / manifest** endpoint, and a **discovery inbox**. Nearly every named vendor connector (ServiceNow, Jira, Signavio, Collibra, Apptio, SaaS/SAP/AI discovery, Teams, Confluence, OData, iPaaS adapter) and the reference catalog are correctly **DEFERRED to PLANV4 15.6**, so they are not counted as parity gaps. The genuinely important, non-deferred gaps are the four foundational primitives above — none of which is vendor-specific and all of which any future connector would depend on.
