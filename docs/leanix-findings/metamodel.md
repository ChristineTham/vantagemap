# Meta Model — LeanIX vs VantageMap

**Scope note.** `metamodel.pdf` (219 pages) is SAP LeanIX's core meta-model documentation. It covers: the layered meta model and its 12 fact sheet types (+ optional System fact sheet); per-type modeling guidelines and subtypes (Application incl. Business Application/Microservice/AI Agent, Business Context, Organization, Interface incl. Logical/API/MCP Server, IT Component incl. Hardware/IaaS/PaaS/SaaS/Service/Software/AI Model, Objective, Platform, Provider, Tech Category, Data Object, Initiative); tags vs. custom fields; the four relation kinds (explicit, parent/child, requires/required-by, transitive); attributes on relations; lifecycle; quality seal; subscriptions/subscription roles; surveys; product-specific modeling best practices (SAP S/4HANA/BTP/ERP 6.0, Microsoft, Google, Salesforce, AWS — pp.100-134); optional meta-model **extensions** (AI Governance, DORA, Contract, Application TCO, SAP Suggestions, IT-Component naming rule — pp.135-164); meta-model **configurability** (custom fact sheet types, subtypes, fields, sections, translations, colors — the v3→v4 configuration walkthrough, pp.165-219); and Meta Model v3 legacy. VantageMap implements the v4 fact-sheet/subtype/relation model almost 1:1 in fixed code (`src/db/schema/*`), so its data model is strongly EQUIVALENT; the principal gaps are all on the *configurability* axis (LeanIX's meta model is fully admin-configurable; VantageMap's is hard-coded) plus visual/diagram features and the advanced compliance extensions.

## Key gaps

- **No configurable meta model (rows 29-32, 24, 31).** This is the single biggest divergence. LeanIX's headline promise is a "fully configurable" meta model: admins create custom fact sheet types, subtypes, fields (with data types, translations, sections, include-in-views/show-in-filters), and rename/recolor types — all without code. VantageMap's model is fixed in pg enums and a static `fact-sheet-config.ts` registry; the admin area only manages users/roles/technical-users. Custom data lives in a schema-less `customFields` jsonb with no field-type metadata or access control. For core EA-tool parity this is the highest-severity gap (effort L).
- **Attributes on relations (row 22).** LeanIX puts key data on the relation itself — cost on app↔IT-component, CRUD usage on app↔data-object, connection method on interface↔app. VantageMap's single generic edge table carries no per-relation field payload, which limits cost reporting and data-flow fidelity (effort M).
- **Transitive/inherited relation roll-up (row 21)** used for hierarchical filtering and landscape aggregation is not clearly implemented beyond GraphQL depth-limited traversal (effort M).
- **Custom-field configuration & calculated fields (rows 24, 42).** No admin field builder and no derived/calculated field engine (effort M).
- **Survey campaigns (row 27):** basic surveys exist but no send/remind/merge-into-fact-sheet workflow (effort M).
- Business-capability maturity is present but simplified (single maturity int vs. current+target+description, row 13, effort S).

## Equivalence summary

On the **data model itself**, VantageMap is a near-exact reproduction of the LeanIX Meta Model v4: all 12 fact sheet types, every documented subtype (down to AI Agent, MCP Server, AI Model, ESG Capability), the standard portfolio attributes (TIME, 6R, fit, criticality), lifecycle, health, quality-seal, tags/tag-groups, subscriptions with RACI roles, and the four relation kinds with a validated relationship-pair table — all match the PDF closely. Where VantageMap falls short is precisely the dimension this document emphasizes most: **configurability**. LeanIX's meta model is admin-configurable end-to-end (custom types, subtypes, fields, sections, translations, colors, calculations) and enriched by discovery/reference-catalog and optional extensions (AI Governance, DORA, Contract, TCO); VantageMap ships a fixed, code-defined model with a jsonb escape hatch and no meta-model admin UI. Net: for out-of-the-box v4 modeling VantageMap is strongly equivalent, but it is not a configurable meta-model platform, and it lacks relation-level attributes, calculated fields, and the compliance/cost extensions.
